# Transaction Explorer Design

## Goal

Make the Local Bitcoin Bank UI explain local wallet transfers in application terms, especially `Alice -> Bob`, while keeping Bitcoin Core as the source of truth for balances, confirmations, timestamps, and block data.

## Scope

This iteration covers:

- remembering which wallet owns each receive address generated by the app;
- recording application metadata when the app sends BTC or uses the faucet;
- enriching transaction history with sender wallet, receiver wallet, address, status, confirmations, time, block hash, and txid;
- showing the enriched history in the existing wallet dashboard.

This iteration does not add a separate block explorer, raw transaction decoder, UTXO screen, or external-address discovery. If an address was not generated by this app, the receiver is displayed as `Unknown address`.

## Architecture

Bitcoin Core remains authoritative for transaction existence, amount, confirmation count, status, time, and block hash. SQLite stores only app metadata: generated address ownership and the wallet-to-wallet relationship inferred when a known address is used.

Two new tables are required:

- `wallet_addresses`: `address`, `wallet_name`, and creation time;
- `app_transactions`: `txid`, sender wallet, optional receiver wallet, receiver address, amount in satoshis, and the latest Bitcoin Core metadata needed by the UI.

The send and faucet services write metadata immediately after Bitcoin Core accepts the transaction. The transaction-history service joins that metadata with `listtransactions`, so pending transactions become confirmed after a later refresh without inventing blockchain data in SQLite.

## API Contract

`POST /wallets/{wallet_name}/address` continues to return the address and also persists its ownership.

`POST /transactions/send` continues to accept `from_wallet`, `to_address`, and `amount_btc`. Its response adds `to_wallet`, which is the mapped wallet name or `null` for an unknown address.

`GET /transactions/{wallet_name}` returns:

```json
{
  "txid": "abc123",
  "category": "send",
  "from_wallet": "alice",
  "to_wallet": "bob",
  "amount_btc": "2.00000000",
  "amount_sats": 200000000,
  "address": "bcrt1...",
  "confirmations": 0,
  "status": "pending",
  "time": 1787030000,
  "blockhash": null
}
```

For an unknown destination, `to_wallet` is `null`. A faucet transaction is recorded as `miner -> target wallet`.

## Error Handling

- A wallet that is not loaded in Bitcoin Core continues to return HTTP 404 through the existing RPC error handler.
- An unknown destination address is valid and does not fail the send; it simply has no mapped receiver wallet.
- A failed Bitcoin Core RPC call must not create an `app_transactions` row.
- History must tolerate missing `blockhash` and missing `time` while a transaction is pending.

## Testing

Backend tests cover address ownership persistence, known and unknown recipients, faucet metadata, and pending-to-confirmed history enrichment. Existing balance, RPC, and endpoint tests remain green. The frontend build verifies the updated TypeScript types and transaction table.
